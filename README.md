# circle-router

Прозрачный VPN-роутер на мини-ПК с двумя ethernet-портами, целиком в Docker Compose.
Интернет заходит в один порт, выходит из другого уже завёрнутым в
[xray-core](https://github.com/XTLS/Xray-core) (VLESS/VMess/Trojan/Shadowsocks,
включая Reality). Управление — веб-панель: DHCP, серверы VLESS, правила обхода,
блокировщик рекламы, замер скорости серверов, графики трафика и потребления.

Идейный предок — [nanopi-vpn-router](https://github.com/tviks/nanopi-vpn-router);
здесь та же схема TPROXY, но systemd-сервисы заменены на контейнеры, а панель
переписана на FastAPI + React.

## Топология

```
[ провайдер: PPPoE или DHCP ]
             │
             ▼
        enp2s0  ── WAN ──┐
                         │
                   [ circle-server ]   xray TPROXY :12345
                         │
        enp1s0  ── LAN ──┘  192.168.10.1/24, DHCP .100–.200
             │
             ▼
   [ свитч / Wi-Fi-точка / клиенты ]
```

## Из чего состоит

| Сервис | Что делает |
|---|---|
| `controller` | REST API, веб-панель, nftables, policy routing, PPPoE, watchdog, метрики, блокировщик, замер скорости |
| `xray` | TPROXY-инбаунд и VLESS-аутбаунд |
| `dnsmasq` | DHCP, DNS и фильтрация рекламы для LAN |

Все три — в `network_mode: host`. `controller` запущен `privileged`: он правит
sysctl'ы хоста, грузит модули ядра и держит `pppd` для PPPoE.

## Быстрый старт

```sh
git clone <repo> circle-router && cd circle-router
bash scripts/gen-env.sh              # спросит пароль, создаст .env
$EDITOR .env                         # проверьте CR_WAN_IF / CR_LAN_IF
docker compose up -d --build
```

Панель — `http://<адрес-роутера>:8088`. С LAN-стороны работает и просто
`http://<адрес-роутера>` без порта: nftables заворачивает 80-й порт,
адресованный самому роутеру, на порт панели.

Дальше в панели: **VPN → Добавить** (или **Из подписки**), сделать сервер
активным, на **Обзоре** включить «Заворачивать трафик в VPN».

## Настройки в `.env`

| Переменная | Смысл |
|---|---|
| `CR_HTTP_PORT` | порт панели, по умолчанию 8088 |
| `CR_ADMIN_USER` / `CR_ADMIN_PASSWORD_HASH` | логин и bcrypt-хеш пароля (генерирует `gen-env.sh`) |
| `CR_SECRET_KEY` | ключ подписи сессионных cookie |
| `CR_WAN_IF` / `CR_LAN_IF` | порты по умолчанию для первого запуска |
| `CR_LAN_ADDRESS` / `CR_LAN_PREFIX` | адрес роутера в LAN |
| `XRAY_VERSION` | тег релиза Xray-core для сборки образа |

Значения из `.env` используются только при первом старте — дальше правда живёт в
`data/config/router.json` и правится через панель.

## PPPoE

**Сеть → WAN → Тип подключения → PPPoE**, логин и пароль провайдера, сохранить.
`pppd` поднимается внутри `controller` и создаёт `ppp0` в сетевом пространстве
хоста; NAT, фаервол и MSS-клампинг автоматически переезжают на `ppp0`.

Что заложено: авто-переподключение (`persist`, `holdoff 5`), контроль сессии
через LCP echo, подгонка MSS под MTU 1492 (без неё часть сайтов виснет, потому
что провайдеры режут ICMP fragmentation-needed), выбор service-name.

Номер интерфейса не фиксирован: после переподключения сессия поднимается как
`ppp0`, `ppp1` и дальше — свободный индекс ядро выбирает само. Поэтому правила
nftables написаны через шаблон `ppp*`, а статус и метрики спрашивают имя у
маршрута по умолчанию. Привязка к `ppp0` оставляла бы реальный интерфейс без
NAT ровно до первого обрыва связи.

Супервизор гарантирует одну сессию: у каждого запуска своё «поколение», а перед
стартом pppd проверяется, не поднят ли он уже кем-то ещё. Две сессии к одному
провайдеру дают два интерфейса с одним адресом и пляшущий маршрут по умолчанию.

## Как устроен роутинг

При включённом VPN:

1. `nftables` в таблице `ip circle_mangle` заворачивает TCP/UDP из LAN в TPROXY
   на `127.0.0.1:12345` и ставит fwmark 1.
2. `ip rule fwmark 1 table 100` + `ip route local 0.0.0.0/0 dev lo table 100`
   заставляют ядро считать эти пакеты локальными — иначе TPROXY их не поймает.
3. xray принимает их `dokodemo-door`-инбаундом, снифает SNI и решает по правилам
   маршрутизации: `proxy` или `direct`.
4. Приватные подсети (`bypass4`) до TPROXY не доходят вовсе — поэтому DNS к
   `dnsmasq` и доступ к самой панели работают всегда.

DNS клиентов: `клиент → dnsmasq на 192.168.10.1:53 → xray на 127.0.0.1:5300 →
upstream`. Резолвинг идёт по тем же правилам, что и трафик, и не утекает мимо VPN.

### Watchdog

Раз в секунду сверяет три факта: стоит ли галка VPN, принял ли xray конфиг с
сервером, слушает ли он TPROXY-порт. Если xray упал или перезапускается,
watchdog за полсекунды снимает TPROXY — LAN уходит в интернет напрямую вместо
того, чтобы на 5–15 секунд остаться без сети, — и возвращает VPN, как только
xray снова поднялся.

### Проверка конфига до перезапуска

Перед тем как перезапустить xray, контроллер прогоняет сгенерированный конфиг
через `xray run -test`. Не прошёл — откат на прямой роутинг, а текст ошибки
показывается в панели. Битая ссылка на сервер не оставит LAN без интернета и не
загонит контейнер в crash-loop.

## Фаервол

Собственные таблицы `circle_filter`, `circle_nat`, `circle_mangle`, `circle_acct`.
Общего `flush ruleset` нет намеренно: он снёс бы цепочки Docker'а вместе с сетью
контейнеров.

Цепочка `input` имеет `policy accept` и гасит лишнее явным `drop` для новых
соединений с WAN. Так промах в правилах оставляет машину открытой, а не
отрезанной, — на headless-роутере это важнее.

### Транзит и Docker

Docker держит свою цепочку `ip filter FORWARD` с `policy drop`, а nftables
требует, чтобы пакет приняли **все** базовые цепочки хука. Наш `accept` в
`circle_filter` этого не отменяет — транзит всё равно умирает у Docker'а.

Поэтому контроллер кладёт разрешающие правила в `DOCKER-USER` — цепочку, которую
Docker вызывает первой и никогда не трогает сам. Правила помечены комментарием
`circle-router`, при каждом «Применить» переставляются заново, а watchdog раз в
полминуты проверяет, что они на месте: перезапуск демона Docker пересоздаёт его
цепочки и вычищает всё лишнее.

После настройки стоит закрыть панель со стороны WAN: **Сеть → Фаервол →
«Панель с WAN»** выключить. Из LAN она останется доступной.

## Учёт трафика

- **Интерфейсы** — счётчики из `/sys/class/net/*/statistics`, опрос раз в 2 с.
- **По клиентам** — dynamic set nftables со счётчиками на каждый IP LAN.
- **VPN против direct** — `xray api statsquery` по тегам аутбаундов.

Живой график держится в памяти (последние ~10 минут), поминутные дельты пишутся
в SQLite и хранятся 30 дней.

## Состояние сервера

На **Обзоре**, под сетевыми графиками, — три карточки о железе. Всё читается из
procfs и sysfs, без внешних утилит и демонов.

- **Процессор**: общая загрузка, полоса на каждое ядро с его собственной
  температурой из `coretemp`, средняя частота, load average и температура
  пакета в шапке карточки.
- **Память**: занято/доступно/кеш и swap, если он есть.
- **Диски**: заполнение каждой файловой системы, температура диска и текущая
  скорость чтения-записи из `/proc/diskstats`.

Температуры берутся из hwmon и раскладываются по типу датчика: `coretemp`,
`k10temp` — процессор, `nvme` и `drivetemp` — диски. `drivetemp` для SATA
загружается автоматически вместе с остальными модулями; без него у SATA-дисков
просто не будет датчика.

Пороги подсветки: загрузка и заполнение желтеют с 60% и краснеют с 85%,
температура — с 70 и 85 °C соответственно.

## Блокировщик рекламы

Фильтрация на уровне DNS: заблокированные домены отвечают `0.0.0.0`, соединение
не устанавливается вовсе. Работает сразу для всех устройств в LAN, включая те,
куда расширение не поставишь — телевизоры, консоли, IoT.

Списки скачиваются, сводятся в один набор доменов и раскладываются в конфиг
dnsmasq строками `address=/домен/0.0.0.0`. Такая запись накрывает домен вместе
со всеми поддоменами, поэтому поддомены с заблокированным родителем из файла
выкидываются — на 180 тысячах доменов dnsmasq занимает около 17 МБ.

По умолчанию включены **AdGuard DNS filter** (~178 тыс. доменов) и **AdAway**
(~6,5 тыс.). В комплекте, но выключены: StevenBlack и OISD small — у OISD
неустойчивый хост, он регулярно отваливается по таймауту.

Парсер понимает четыре формата, так что добавить можно почти любой публичный
список: AdBlock (`||domain^`), hosts (`0.0.0.0 domain`), dnsmasq (`local=/d/`)
и просто перечисление доменов.

Свои правила — в разделе «Свои правила»: **Блокировать** добавляет домены к
спискам, **Разрешить** пробивает исключение (в dnsmasq выигрывает более длинное
совпадение, поэтому исключение сильнее любого списка).

Скачивание идёт в фоне (по умолчанию раз в сутки) и не блокирует ни старт
контроллера, ни кнопку «Применить»: скачанные списки лежат в
`data/cache/adblock/`, а пересборка файла берёт их оттуда.

**Статистика.** dnsmasq пишет запросы в stderr, docker забирает поток и ротирует
его сам, а контроллер читает и считает: сколько запросов, сколько заблокировано,
какие домены и клиенты в топе. Отключается галкой «Считать запросы».

## Замер скорости серверов

Кнопка **Замерить все** (или молния у конкретного сервера) поднимает временный
экземпляр xray с одним этим аутбаундом и локальным HTTP-инбаундом, качает через
него файл с Cloudflare и считает скорость. Основной xray не трогается — клиенты
в LAN ничего не замечают.

Отсчёт начинается с первого байта, чтобы TLS-handshake не портил цифру. Замер
идёт `speedtest.duration` секунд (по умолчанию 8): Cloudflare отдаёт не больше
~50 МБ за запрос — быстрый канал съедает их меньше чем за секунду, поэтому файл
качается в цикле, пока не выйдет время. Кроме скорости показываются отклик,
выходной IP и страна выхода — сразу видно, куда на самом деле приземляется
трафик.

Замер съедает реальный трафик: восемь секунд на гигабитном канале — это
примерно 700 МБ на сервер. На лимитном тарифе уменьшите `duration` в
`router.json` или проверяйте серверы по одному.

Результат последнего замера хранится в `router.json` рядом с сервером и
переживает перезапуск.

## Проброс портов

**Сеть → Проброс портов**. Правило описывается пятью полями: протокол, внешний
порт, адрес устройства в LAN, его порт и (необязательно) ограничение источника —
IP или подсеть, откуда пускать.

Под капотом — `dnat` в `circle_nat`, плюс три вещи, без которых проброс работает
через раз:

- **Hairpin.** Изнутри сети домен резолвится во внешний адрес роутера, и пакет
  приходит на LAN-порт, а не на WAN — правило для входящих его не видит. Поэтому
  на каждое правило ставится второе, с `fib daddr type local`: оно ловит
  обращение к любому собственному адресу роутера и переживает смену IP
  провайдером. Плюс маскарад на обратный путь — иначе ответ пришёл бы клиенту
  напрямую от соседа по подсети, и тот бы его отбросил.
- **TPROXY не трогает свои адреса.** Без `fib daddr type local accept` в mangle
  обращение изнутри к внешнему адресу роутера уезжало в VPN вместо DNAT.
- **Разрешение в forward.** `nat prerouting` отрабатывает раньше `filter
  forward`, так что проброшенные пакеты уже помечены conntrack'ом: одно правило
  `ct status dnat accept` покрывает все правила сразу.
- **Цепочка Docker.** Тот же `ct status dnat accept` кладётся в `DOCKER-USER`,
  иначе `policy drop` съест входящие соединения (см. раздел про транзит).

### Устройство за другим роутером

Роутер пробрасывает только в свою подсеть. Если сервис стоит за нижестоящим
роутером (двойной NAT), проброс делается в две ступени:

```
интернет ─▶ наш роутер: 443 → <адрес нижнего роутера в LAN>:443
                          └─▶ нижний роутер: 443 → <адрес сервиса>:443
```

В поле «Куда» указывается адрес промежуточного роутера, а не конечного
сервиса — панель об этом прямо скажет, если ввести адрес из чужой подсети.
Адрес промежуточного роутера стоит закрепить резервацией DHCP, иначе однажды
он сменится и проброс тихо перестанет работать.

Проброс порта 22 и порта самой панели запрещён валидацией: DNAT увёл бы SSH и
веб-интерфейс мимо роутера, а на headless-железке это билет в один конец.
Дубликаты по паре «протокол + внешний порт» тоже отлавливаются до применения.

Если WAN-адрес приватный (роутер стоит за другим роутером, как сейчас за
`192.168.31.1`), панель об этом предупредит: правило откроет порт для сети
аплинка, но чтобы он был виден из интернета, такой же проброс нужно сделать и на
вышестоящем роутере — на адрес нашего WAN.

## Доступ к сети аплинка

Сеть, в которую воткнут WAN-порт (домашний роутер с NAS, принтером, камерами),
настраивается в **Сеть → Доступ к сети аплинка**. Подсети определяются
автоматически по адресу WAN, при желании задаются вручную.

| Переключатель | Что делает | Нужен маршрут на роутере аплинка |
|---|---|---|
| Клиенты LAN видят сеть аплинка | включён по умолчанию, работает через NAT | нет |
| Сеть аплинка видит LAN | снимает запрет на входящие WAN → LAN | да |
| Без NAT в сторону аплинка | хосты аплинка видят настоящие адреса клиентов | да |

Два последних переключателя требуют статического маршрута на роутере аплинка:
`192.168.10.0/24` через адрес WAN-порта роутера. Без него пакеты уйдут, а
вернуться не смогут. Панель показывает нужную строку прямо под переключателями.

Сеть аплинка автоматически попадает в bypass TPROXY — иначе при включённом VPN
запросы к NAS уезжали бы на VPN-сервер и терялись.

## Смена пароля

**Система → Пароль панели**. Новый bcrypt-хеш ложится в
`data/config/auth.json` — перезапуск контейнера не нужен, и пересборка образа
его не затирает. Значение `CR_ADMIN_PASSWORD_HASH` из `.env` используется только
при первом запуске, когда файла ещё нет.

Смена пароля поднимает счётчик `epoch`, а он входит в подпись cookie — все
сессии на других устройствах обрываются немедленно. Браузеру, из которого меняли
пароль, сразу выдаётся новая cookie, так что разлогиниться самому себе нельзя.

## Грабли, которые здесь уже обойдены

1. **`mark` в sockopt TPROXY-инбаунда** — бесконечная петля. Принятые сокеты
   наследуют `SO_MARK`, ответы клиентам попадают в policy-route на `lo` и
   возвращаются в xray. Правильно: `sockopt: {"tproxy": "tproxy"}` без `mark`.
2. **`sockopt.mark` на аутбаунде** — то же самое для исходящих. Импортированные
   из подписки аутбаунды санитайзятся: `mark` вырезается.
3. **`tcpSettings.header.type=http` без запроса** ломает handshake Reality.
   Добавляется только при явном `headerType=http` в ссылке.
4. **UDP через VLESS+TCP** не идёт без `xudp`. QUIC (UDP/443) блокируется —
   браузеры откатываются на TCP и идут через VPN; остальной UDP — direct.
5. **`flush ruleset`** убил бы правила Docker'а. Только свои таблицы.
6. **`rp_filter=1`** дропает TPROXY-пакеты до nftables. Сбрасывается в 0.
7. **netplan/networkd** отбирает адрес у LAN-порта. Пишем ему `Unmanaged=yes`, а
   watchdog всё равно возвращает адрес, если тот пропал.
8. **`240.0.0.0/4` уже включает `255.255.255.255/32`** — вместе nft ругается
   `conflicting intervals`.
9. **Дубли `ip rule`**: перед добавлением старые правила вычищаются в цикле,
   иначе каждое «Применить» плодит копии.
10. **Путь lease-файла** в `dnsmasq.conf` — в координатах контейнера dnsmasq
    (`/etc/dnsmasq`), а не контроллера (`/data`). Разные точки монтирования
    одного каталога.
11. **`xray run -test` определяет формат по расширению файла.** Кандидат с
    именем `*.tmp` он не читает вовсе — нужен либо `.json`, либо `-format=json`.
    Ещё ему нужен `XRAY_LOCATION_ASSET`, иначе проверка падает на `geosite:*`.
12. **Скачивание списков блокировки на старте** повесило бы `reconcile` на
    минуту. Сборка из кеша и фоновое скачивание разведены: при отсутствии кеша
    источник помечается «ещё не скачан», а не тянет мегабайты синхронно.
13. **Порядок `**` в словаре Python.** В `/api/status` спред `uplink_access`
    стоял после вычисленных подсетей и затирал их одноимённым пустым полем из
    конфига — панель показывала «подсети не определены» при рабочих правилах.
14. **`FORWARD policy drop` от Docker** — самая коварная из всех. Своя таблица
    с `policy accept` ничего не меняет: в nftables пакет должны принять все
    базовые цепочки хука. Симптом обманчив — при включённом VPN интернет у
    клиентов работает (TPROXY доставляет пакеты локально, мимо FORWARD), а
    молча отваливается ровно то, что идёт в обход прокси: сеть аплинка и весь
    транзит при выключенном VPN, то есть аварийный откат watchdog'а.
    Лечится правилами в `DOCKER-USER`, а не правкой `policy` — Docker её
    восстановит.
15. **TPROXY съедал ответы проброса.** Ответ проброшенного соединения идёт из
    LAN на публичный адрес клиента и выглядит как обычный исходящий трафик —
    правило `iifname LAN … tproxy` утаскивало его в xray, соединение
    рассыпалось, а инициатору прилетал RST от нашего же роутера. Лечится
    `ct status dnat accept` в mangle-цепочке ДО правил tproxy.
16. **`reconcile` не трогал mangle-цепочку.** Её переписывал только watchdog и
    только на переходах вкл/выкл, так что правки bypass-списков и проброса
    висели в старой редакции до ближайшего падения xray.
17. **Шаблон `ppp*` в наборе nftables работает** — вопреки ожиданию, что в
    сетах только точное совпадение. Проверено счётчиками: `iifname { "enp2s0",
    "ppp*" }` ловит ppp1 наравне с одиночным `iifname "ppp*"`.
18. **`/hostfs/proc/mounts` бесполезен.** `/proc/mounts` — симлинк на
    `self/mounts`, и procfs отдаёт таблицу того, кто читает: через смонтированный
    корень хоста всё равно видно монтирования контейнера. Зато рекурсивный bind
    создаёт настоящие записи в нашей же таблице с префиксом `/hostfs` — их и
    разбираем.
19. **Корень хоста нельзя монтировать в `/host`,** если туда же уже монтируется
    что-то вложенное: Docker не может создать точку внутри read-only бинда и
    вообще не запускает контейнер. Отсюда отдельный `/hostfs`.
20. **Опрос затирал заполняемые формы.** `usePoll` отдаёт каждый раз новый
    объект, даже когда данные не изменились. Эффект вида
    `useEffect(() => setDraft(config), [config])` срабатывал на каждом тике, и
    всё набранное в полях исчезало — раз в тридцать секунд, посреди
    заполнения. Лечится флагом «есть несохранённые правки»: пока он поднят,
    серверная версия в форму не попадает (`useConfigDraft`).
21. **Валидация не должна прерывать `reconcile`.** Одно недозаполненное
    правило проброса роняло весь проход — вместе с подъёмом PPPoE. После
    перезапуска контроллера дом оставался без интернета из-за опечатки в
    форме. Теперь негодные правила просто не попадают в ruleset, а претензии
    уходят в отчёт; сеть поднимается в любом случае.
22. **Выключенное правило тоже блокировало применение** — валидация обходила
    все правила подряд, не глядя на флаг. Недозаполненная заготовка намертво
    вешала кнопку «Применить».
23. **Hairpin — это отдельное правило, а не следствие проброса.** Снаружи
    работает, изнутри нет: пакет к внешнему адресу приходит на LAN-порт, и
    правило `iifname WAN … dnat` его не видит. Симптом обманчив — «с телефона
    по мобильному интернету открывается, с ноутбука дома нет».
24. **`docker exec … reconcile()` — отдельный процесс.** У него своё состояние
    модуля, поэтому он считает, что pppd никто не поднимал, и запускает вторую
    сессию. Применять конфиг нужно через API панели, а не мимо неё.
